Mechanism (CPython 3.9.25 multiprocessing.pool, /usr/lib64/python3.9/multiprocessing/pool.py):
1. Pool.__exit__ calls terminate(). _terminate_pool (line 692) calls _help_stuff_finish (669-675), which ACQUIRES inqueue._rlock and never
   releases it, while the task handler thread puts one None sentinel per worker into the inqueue. Workers that obtain the rlock before the
   parent read their sentinel and exit normally (seven did); workers that lose the race block on the rlock forever.
2. CPython then relies on p.terminate() (SIGTERM) to kill the blocked workers before p.join(). campaign860.py:827 installs
   signal.signal(SIGTERM, request_stop) in the parent BEFORE the forks (main -> run -> initialize), and fork-pool workers inherit the
   Python-level handler, which only sets STOP = True. So SIGTERM is swallowed in the workers, the blocked worker never exits, and the
   parent's p.join() waits forever.
3. The same `with Pool` pattern is used by origin860.py:158 (Jacobian origin columns), so every trial (validate) and every epoch start
   (Jacobian) of the campaign driver is exposed. bench860, assess860 and T4 install no SIGTERM handler, so the default disposition kills the
   blocked workers and they never hang; the development campaign roots did not exercise the real fork pools under the handler.
4. Consequence if nothing is done: the guard's max_seconds 6600 ends the slice at about 02:06:34Z as a process fault; the supervisor restarts
   with backoff and the initialization validate hangs again with the same probability.

Options for the lead:
A. Immediate, result-neutral unblock: SIGKILL the stuck pool worker 3996603 only. pool.map had returned all parts; killing the idle worker
   makes p.join() return, Pool.__exit__ completes, validate returns the complete result, initialization proceeds. Every later Pool exit
   (validate, Jacobian) can hang again and would need the same manual unblock (or a watchdog that kills only an idle, zero-CPU pool worker
   whose parent is in _terminate_pool join; detection via /proc wchan and py-spy).
B. Code fix (new manifest tag, lead and verifier review; no arithmetic changes): in campaign860.py main(), before the fork sites, reset the
   signal disposition in forked children: os.register_at_fork(after_in_child=lambda: (signal.signal(signal.SIGTERM, signal.SIG_DFL),
   signal.signal(signal.SIGINT, signal.SIG_DFL))). Pool.terminate then kills idle workers as CPython expects. Draft:
   outputs/dev_v9/pending_g4v2/campaign860.py (one added line; diff in outputs/dev_v9/pending_g4v2/DIFF.txt). Alternative fix in the
   numerical modules: replace `with ctx.Pool(procs) as pool: parts = pool.map(...)` by pool.close(); pool.join() (graceful sentinel shutdown,
   no rlock hold, no SIGTERM) in fields860.residual_parallel and origin860.residual_series; arithmetic unchanged.
C. Stop the pilot cleanly now (SIGTERM to the supervisor, then the guard) and relaunch after B is frozen; the seed assessment record stays.
Note: with the inherited handler, a guard SIGTERM to the process group was never able to end a trial within the 120 s grace (a trial lasts
about 900 s), so the SIGKILL fallback decided every guard stop in any case; option B does not weaken that path.
